1. Présentation

Ce document décrit l'installation, la configuration, l'exploitation et le dépannage de l'application de réservation de billets de bus de Ma Compagnie. Il s'adresse à la personne qui gère le serveur.

L'application comprend un site de réservation pour les voyageurs, un back-office pour le personnel (adresse /admin) et une API qui garantit qu'un siège n'est jamais vendu deux fois. Chaque société dispose de sa propre installation et de sa propre base de données.

À savoir — Seul le service web est exposé sur Internet (ports 80 et 443). La base et Redis ne sont accessibles que depuis le réseau interne de Docker.

Comment la double vente est empêchée

Chaque siège occupé d'un voyage est une ligne de la table trip_seats, dont la clé primaire est (trip_id, seat_no). PostgreSQL refuse donc physiquement qu'un siège existe deux fois. Le verrou temporaire et la vente sont la même ligne : passer de « verrouillé » à « vendu » se fait dans une seule transaction. Les écrans ne sont jamais la source de vérité.

3. Installation

Prérequis

  • Serveur Linux (Ubuntu 22.04 ou plus récent conseillé) : 2 vCPU, 4 Go de RAM, 40 Go de disque.
  • Docker Engine et le plugin Docker Compose.
  • Un nom de domaine dont l'enregistrement DNS A pointe vers le serveur.
  • Ports 80 et 443 ouverts vers Internet.

Procédure

  1. Copier le dossier du produit sur le serveur (par exemple dans /opt/busbooking).
  2. Lancer le script d'installation avec le nom de domaine.
  3. Noter le code d'installation affiché à la fin.
  4. Ouvrir le site : l'assistant de première configuration démarre.
cd /opt/busbooking/deploy
./scripts/install.sh reservation.masociete.mg

Le script crée le fichier deploy/.env avec des secrets générés aléatoirement, construit les images, démarre les services et attend que l'API réponde. Le certificat HTTPS est obtenu automatiquement au premier accès.

Attention — Faites immédiatement une copie du fichier deploy/.env dans un endroit sûr, hors du serveur. La variable APP_ENCRYPTION_KEY est indispensable pour relire les clés de paiement et le mot de passe SMTP après une restauration.

Essai sur un poste de travail

./scripts/install.sh localhost      # puis ouvrir https://localhost (certificat auto-signé à accepter)

Réglages dans le back-office

Le menu Société et réglages reprend tous les groupes de l'assistant et ajoute : Modèles d'e-mails (objet et texte de chaque message, avec variables comme {{company_name}} ou {{reference}}), Textes et langues (modifier un texte du site ou ajouter une langue) et Sécurité (rôles pour lesquels la double authentification est obligatoire, durée des sessions, nombre d'essais de connexion).

Secrets

Les clés des opérateurs de paiement et le mot de passe SMTP sont chiffrés en AES-256-GCM avec APP_ENCRYPTION_KEY avant d'être enregistrés. Ils ne sont jamais renvoyés au navigateur : l'écran indique seulement qu'une valeur est enregistrée.

Espèces au guichet—Au guichet

Simulateur

En mode test, sans clés saisies, le paiement est simulé : aucun débit réel. Les quatre derniers chiffres du numéro payeur pilotent le résultat.

Numéro terminé parRésultat simulé
0000Paiement refusé
0001Aucune réponse de l'opérateur (la réservation expire)
0002Paiement confirmé en retard, après l'expiration du verrou
autrePaiement accepté après quelques secondes

Cycle d'un paiement

  1. Le voyageur valide : l'API crée le paiement et prolonge le verrou des sièges pendant le délai de paiement.
  2. L'opérateur envoie une demande de validation sur le téléphone du voyageur.
  3. La confirmation arrive par callback, à une adresse signée propre à ce paiement. Sans callback, une tâche interroge l'opérateur à intervalles croissants.
  4. À la confirmation, l'API vérifie que les sièges sont toujours réservés pour ce voyageur, émet les billets et envoie l'e-mail.
  5. Si la confirmation arrive après que le siège a été revendu, la réservation est annulée et un remboursement est créé. Il n'y a jamais deux billets pour un siège.
Attention — Les connecteurs MVola, Orange Money et Airtel Money sont écrits d'après la documentation publique des opérateurs. Ils n'ont pas été exécutés contre les opérateurs. Avant de passer un moyen en « Production », faites un paiement d'essai complet en bac à sable avec les identifiants de Ma Compagnie.

12. Sauvegarde et restauration

Le service backup sauvegarde chaque jour, à l'heure BACKUP_HOUR, la base de données et les fichiers envoyés (logos, images). Les archives sont dans deploy/backups : daily (7 jours), weekly (5 semaines) et monthly (6 mois).

./scripts/backup.sh                                              # sauvegarde immédiate
./scripts/restore.sh backups/daily/backup-AAAAMMJJ-HHMMSS.tar    # restauration complète
Attention — La restauration remplace toutes les données actuelles. Le script arrête le site, demande de taper RESTAURER, restaure, puis redémarre.
  • Copiez régulièrement le dossier deploy/backups hors du serveur : une sauvegarde qui reste sur le même disque ne protège pas d'une panne.
  • Faites un essai de restauration sur un serveur de test au moins une fois par trimestre.
  • Si BACKUP_PASSPHRASE est définie, les archives portent l'extension .enc et la même phrase est nécessaire pour restaurer.

13. Mise à jour

  1. Placer la nouvelle version du code dans le dossier du produit (copie ou git pull), sans toucher à deploy/.env ni à deploy/backups.
  2. Lancer ./scripts/update.sh depuis deploy/.
  3. Le script fait une sauvegarde, reconstruit les images, redémarre et vérifie que l'API répond. Les migrations de base s'appliquent au démarrage.
  4. En cas d'échec, restaurer la sauvegarde qui vient d'être faite avec l'ancienne version du code.

Désactiver la double authentification d'un compte en urgence

docker compose --env-file .env exec db psql -U busbooking busbooking \
  -c "UPDATE users SET totp_enabled = false, totp_secret_enc = NULL, recovery_codes = '[]' WHERE lower(email) = 'admin@masociete.mg'"

La personne se connecte ensuite avec son mot de passe et réactive la double authentification depuis son profil.

18. Limites connues

  • Les images Docker n'ont pas été construites ni exécutées pendant le développement (pas de Docker disponible). Le fichier Compose est validé syntaxiquement ; la configuration Caddy, la sauvegarde et la restauration ont été exécutées hors conteneur.
  • Les connecteurs de paiement réels sont à valider en bac à sable avec des identifiants marchands.
  • L'envoi d'e-mails a été testé contre un serveur SMTP de test, pas contre un fournisseur réel.
  • Le contrôle des billets par la caméra dépend du navigateur ; un lecteur de codes ou la saisie du numéro fonctionnent partout.
